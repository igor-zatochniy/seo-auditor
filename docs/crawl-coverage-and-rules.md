# Повнота обходу, власні правила та фільтри URL

Усі перевірки локальні, без платних API. GSC і серверні журнали — опційні джерела, які імпортує користувач. Інструмент не перевіряє позиції Google, не підтверджує індексацію чи AI-цитування та не змінює сайт/robots.txt.

## Карта спостережених URL

Вкладка **Повнота обходу** доступна для Site Crawl. Реєстр окремий від frontier: знайдений URL зберігається навіть тоді, коли досягнуто ліміту сторінок чи глибини. Також зберігаються nofollow-спостереження. Первинні результати, кількість targets і рішення crawler не змінюються.

- Джерела: стартова ціль, HTML/DOM-посилання, sitemap, GSC, імпортований журнал ботів.
- Стани: результат збережено, robots, помилка, очікує, відсутній результат, ліміт глибини/сторінок, nofollow, URL не знайдено обходом.
- Нуль спостережених inlinks дає **кандидата** без вхідних посилань, не доведену orphan page. Дані не означають повного обходу сайту навіть без спрацювання лімітів.
- Важливі URL можна позначити вручну або під час імпорту. Окремо показуються важливі адреси без успішного результату. Автоматичного запиту замаскованого URL немає: для повторного аудиту чутливої адреси потрібен її оригінал.

Реєстр обмежений 50 000 URL на run. Після досягнення ліміту відомі записи оновлюються, нові не додаються; звіт явно показує неповноту. SQL-читання пагіноване за fingerprint, записи зберігаються пакетами до 256. Немає RAM-мапи всього сайту.

Sitemap discovery має попередні обмеження: 16 файлів, 2 MiB декодованого XML, 100 000 XML-токенів і 2 хвилини. Один файл читає до `max(max_pages,5000)` URL; відомі адреси поза frontier зберігаються в реєстрі. Решта sitemap за межами бюджету не завантажується й позначається partial. Реєстр не є повним зовнішнім індексом.

Для історичних аудитів до міграції 38 є лише fallback зі збережених nodes. Вони залишаються позначеними як legacy/partial навіть після імпорту нового джерела. Старі edges/URL не відновлюються з замаскованих значень.

### Імпорт GSC

CSV до 2 MiB / 5000 рядків із колонкою `Page`, `URL`, `Top pages` або `Сторінка`. Інші колонки не використовуються: покази чи кліки не перетворюються на доказ індексації.

```csv
Page,Clicks,Impressions
https://example.com/catalog,38,1420
https://example.com/about,12,800
```

URL повинен належати тому самому origin. Некоректний чи сторонній рядок відхиляє весь імпорт, без часткових записів. Більше 5000 рядків — помилка, не мовчазне усічення. UUID/digest роблять повтор ідемпотентним. Не більше 32 зовнішніх джерел на run.

### Журнали ботів

Кнопка **Журнал ботів** приєднує вже наявний імпорт із модуля ботів. Нових HTTP-запитів до сайту немає. Беруться лише URL того самого origin і того самого HMAC-ключа. Зберігаються часовий діапазон, кількість записів і кількість збігів з офіційним IP-діапазоном; останнє не є абсолютною перевіркою особи бота. User-Agent не стає підтвердженим ботом.

Повторне приєднання того самого журналу не подвоює дані. Різні журнали можуть мати перетини: лічильник — імпортовані записи, не гарантована кількість унікальних відвідувань. Старі імпорти без key check потрібно повторно імпортувати. За підтвердженим HMAC доповнюються лише нові метадані ідентичності; історичні HTTP/IP-результати не змінюються.

Оригінальні query values не зберігаються в новому реєстрі. Identity — HMAC оригінального нормалізованого URL до redaction; замаскована адреса не використовується для дедуплікації. Ротація потребує нового key ID; сторонній ключ не використовується для злиття історії.

## Власні правила

У **Моніторингу** кнопка **Власні правила аудиту** відкриває набір конкретного розкладу. До 32 правил, пріоритет critical або warning, точний шлях/URL без query або один * наприкінці для шляху. Query не входить до області правила. Довільні regex, JavaScript, SQL чи зовнішні виклики не підтримуються.

Типи: http_200, indexable (технічні директиви Google, не факт індексації), self_canonical (оголошені HTML/HTTP canonical), canonical_prefix (той самий origin і префікс), canonical_changed (відбиток повного набору canonical), content_drop (відсоткове скорочення наявного word count), product_price (кожен зібраний Product має числову ціну offers/priceSpecification), oai_search_allowed (відоме правило OAI-SearchBot для URL). Поріг контенту обмежений 1–90%; сповіщення можна відкласти на 1–10 послідовних запусків.

Product evidence використовує обмежений JSON-LD collector; підтримує inline offers і локальні @id. Невідоме/неповне посилання, ліміт чи некоректний блок дає **недостатньо даних**, не вигадану відсутність ціни. Це не повна перевірка Google rich results. Правила аналізують response HTML, не всі стани JavaScript.

Якщо URL заборонений `robots.txt`, правило, якому потрібен HTML (`indexable`, canonical або Product), має стан **unknown**: вміст не отримано, тож наявність `noindex` чи canonical не встановлена. `http_200` оцінюється окремо за фактично збереженим HTTP-кодом. Заборона обходу сама по собі не є доказом заборони індексації.

Перед запуском розкладу правила та ревізії фіксуються разом з audit run. Наступне редагування не змінює цей знімок. Optimistic revision захищає від перезапису налаштувань іншим вікном. Для старого завершеного аудиту можна явно застосувати незмінний ручний знімок; він не стає baseline планового моніторингу.

Після аудиту scheduler обробляє до 100 сторінок за транзакцію: результати, події й cursor фіксуються атомарно. Після перезапуску робота продовжується з cursor. Політика має `pass`, `fail`, `unknown`; failed/canceled SEO-run не оголошує порушення виправленими. Поява/виправлення порівнюється лише з останнім перевіреним станом того самого schedule, fingerprint, ключа та ревізії. Unknown не закриває порушення. Перша відома помилка позначається як вперше спостережена, не доведена нова регресія.

Події входять до наявного журналу сповіщень; їх можна підтвердити позначкою прочитання. Для конкретного правила можна додати тимчасове виключення лише для URL, який уже зустрічався в історії цього розкладу та відповідає області правила; зберігаються HMAC fingerprint, замаскований URL, причина та строк дії, але не вихідний query. Ліміт — 500 активних винятків на розклад, і UI показує їх повністю. У редакторі показується час останнього сповіщення. SEO-results не переписуються. Для адаптивного розкладу нове product-price правило не використовує старий 304 snapshot без відповідних метаданих: буде повний GET. Retention зберігає pending jobs і останні baseline.

## Сімейства фільтрів

Вкладка **Фільтри URL** групує спостережені адреси за origin + path. Показує кількість HMAC-варіантів, аудитовані сторінки, повторні точні текстові підписи, non-self canonical, директиви Google, максимальну кількість параметрів, числову пагінацію та записи ботів.

Значення query не зберігаються. Для діагностики є лише до 16 нормалізованих назв параметрів і діапазон числової пагінації `page/p/offset/start`: ≤10, 11–100, 101–999 або ≥1000, не вихідне число. Назви нестандартної форми, усічення й неповні метадані позначаються. Діапазон пагінації не є crawl depth. Порівнюються лише повні підписи тексту тієї самої моделі з достатнім контентом, не весь HTML.

Евристики для ручної перевірки: від 20 варіантів з багатьма дублями/non-self canonical, від 50 варіантів з 3+ параметрами, від 20 варіантів із числовою пагінацією ≥1000. Це не прогноз усіх можливих URL і не вимір Google crawl budget. Signed URLs, мовні та товарні варіанти можуть бути навмисними. Не всі схожі адреси є SEO-проблемою. Автоматичних Disallow/noindex/canonical змін немає.

## Оновлення

Міграція 043 додає спостережені значення, лічильник послідовних порушень, час останнього сповіщення та обмежені виключення правил. Попередні міграції не змінюються; для цього binary потрібна схема 43. Перед оновленням робочої БД створіть backup і використовуйте узгоджений binary.

# Журнали ботів, адаптивний аудит і JSON-LD

Усі три модулі працюють без платних API. PostgreSQL залишається основним сховищем. Інтерфейс доступний лише через наявні localhost/token/same-origin перевірки.

## Журнали ботів

Розділ `/bots` приймає Nginx JSONL або Nginx/Apache combined: до 8 МіБ, 10 000 непорожніх рядків, 8 КіБ на рядок. Аналізуються GET/HEAD-запити. Перевищення відхиляє весь імпорт, а не приховує усічення. Некоректні, звичайні браузерні й сторонні доменні рядки мають окремі лічильники. Відносні request URI інтерпретуються як HTTPS; для HTTP використовуйте абсолютні URL у журналі.

JSONL підтримує `time` / `time_iso8601` (RFC3339), `remote_addr`, `request` / `request_uri`, `user_agent` / `http_user_agent` і числовий або рядковий `status`:

```json
{"time":"2026-10-13T09:00:00Z","remote_addr":"66.249.66.1","request":"GET /page HTTP/1.1","user_agent":"Googlebot/2.1","status":200}
```

IP-списки Google common crawlers, OAI-SearchBot, GPTBot і ChatGPT-User завантажуються лише з фіксованих офіційних HTTPS-джерел. Приватні адреси й redirect від джерела не дозволені; кожна відповідь обмежена 512 КіБ і 4096 діапазонами. Оновлення явне, термін придатності локального списку — 7 днів. Збій не замінює попередній список некоректними даними.

`matched_range` — збіг заявленого IP з поточним офіційним списком, `range_mismatch` — невідповідність, `unverified` — немає придатного списку/IP. Для ClaudeBot наразі немає IP-перевірки. User-Agent сам по собі не підтверджує бота. За CDN потрібен надійний клієнтський IP із налаштованого журналу: довільному `X-Forwarded-For` модуль не довіряє.

Це аналіз наданих вами журналів, не незалежна атестація їхньої справжності. Поточні IP-списки не доводять історичну належність IP. Візит не підтверджує індексацію, AI-видимість чи цитування; GPTBot не прирівнюється до ChatGPT Search.

Сирі журнали, IP, User-Agent та query values не зберігаються. У PostgreSQL потрапляють замаскований URL, HMAC ідентичності, бот, HTTP-код, час та результат перевірки. Різні signed URL не зливаються через redaction. Імпорт атомарний; повтор ID/того самого файлу не дублює дані й не переписує початкову оцінку. Файли з частково перекривними періодами автоматично не дедуплікуються: використовуйте неперекривні експорти. UI показує останні 100 імпортів, звіт пагінується по 100 URL/бот/verification груп. Квота — 1000 імпортів.

## Адаптивний повторний аудит

У формі `/monitoring` є опційний адаптивний режим **для списку URL без JavaScript**. Повний Site Crawl і автоматичний GEO-моніторинг залишаються окремими фіксованими розкладами; GEO-профіль не можна прив'язати до часткових adaptive snapshots.

Кожен URL має власний наступний час, пріоритет 1–3, кількість стабільних перевірок і послідовних помилок. Homepage отримує високий пріоритет; інші URL — звичайний. Пріоритет можна змінити у списку цілей. Стабільні повні метрики поступово збільшують інтервал у заданих межах 1–720 годин; зміни/збої повертають мінімальний інтервал. Це евристична пріоритезація, не доказ незмінності всього сайту.

Одна чергова перевірка містить не більше 50 належних URL. Решта не зникають: залишаються у PostgreSQL і потрапляють у наступні пакети. «Запустити зараз» також перевіряє лише один пакет. Зберігаються нові `run_id` і результати; попередні аудити не переписуються. Для кожного URL фіксується його власний baseline, а не довільний попередній частковий запуск.

Умовний GET використовує валідні `ETag` / `Last-Modified`. Robots перевіряється до запиту. `304` дозволяє повторно використати лише повний успішний знімок того самого URL, HMAC-ключа та моделі SERP; `http_response_status=304` і `reused_from_run_id` явно показують походження метрик. `status_code=200` описує збережену representation, не новий HTTP transfer. Час такого запиту не є виміром повного завантаження сторінки. Зміна `X-Robots-Tag` змушує виконати повний GET. Кожна п'ята стабільна перевірка є повною; після досягнення межі стабільного лічильника також виконується повне завантаження. Не можна покладатися на некоректні validators сервера як на доказ незмінності контенту.

Нові noindex/robots/canonical зміни повідомляються одразу. HTTP/мережеві помилки — після 1–10 послідовних збоїв, типово двох; сповіщення виникає на перетині порога, а не кожного наступного разу. Порівняння, події, baseline і наступний час фіксуються однією транзакцією. Невизначений COMMIT не повторюється сліпо. Stale run recovery наявного scheduler охоплює й ці запуски. Retention захищає baseline кожної цілі та незавершених порівнянь.

Вихідні URL залишаються **лише у захищеній конфігурації розкладу**, як у звичайному scheduler. HTTP validators у кеші шифруються AES-GCM окремо виведеним ключем: навіть відбитий сервером token не зберігається у plaintext ETag. Ротація ключа або пошкоджений ciphertext вимикають conditional reuse і спричиняють повний GET. Пауза не видаляє джерело розкладу; контрольоване `retention --forget-schedule` потребує явного застосування до вимкненого розкладу. Не додавайте одноразові reset/OAuth/signed URL у постійні розклади.

Деталі SEO-сторінки мають точковий recrawl з новим запуском. Для замаскованих query URL потрібен оригінал і перевірка HMAC; після ротації ключа створіть новий звичайний аудит. Звичайний recrawl не використовує adaptive cache.

## JSON-LD

Діагностика додається до звичайного потокового HTML-парсингу й DOM-знімка після JavaScript. Перевіряються синтаксис/byte offset, локальні `@id` між блоками, суперечливі назви/типи, підозріле повторне HTML-екранування та вибрані властивості Product, Article, Organization, BreadcrumbList/ListItem. Немає зовнішніх запитів за `@context` чи `@id`.

Правила Product стосуються **product snippets**, не повної merchant-listing валідації. Властивості Article/Organization позначаються рекомендаціями, а не універсальними помилками. Це локальний linter, не повна JSON-LD expansion, Google Rich Results Test або гарантія rich results/AI-цитування. Відсутність JSON-LD сама по собі не є помилкою.

Межі: 64 блоки, 64 КіБ на блок / 256 КіБ на сторінку, 2048 вузлів, глибина 16, 128 локальних ID/посилань і 64 повідомлення. Неповна перевірка позначається явно, без висновку про відсутність сутностей. У повідомленнях немає вихідного JSON, ID чи довільних значень/ключів. SQL зберігає лише bounded diagnostics; HTML/UI екранують текст.

## Оновлення та перевірки

Потрібні нові міграції **032–034**; раніше застосовані файли не змінювалися. Перед оновленням робочої БД потрібен backup. Binary очікує схему 34. Down 34 видаляє лише adaptive state/cache і нові HTTP provenance колонки; Down 33 видаляє Bot Analytics; Down 32 — JSON-LD diagnostics. SEO/GEO результати залишаються, але для повного відкату стану потрібен узгоджений backup і старий binary. Автоматичний cleanup/rollback робочих даних не виконується.

```powershell
go test -race -count=1 ./...
go test -tags=integration -run 'Test(AdaptiveConditionalAuditLifecycle|AdaptiveAuditUsesBoundedSnapshots|BotImportIdempotencyAndURLIsolation|MonitoringExtensionsUpgradePreservesExistingReports)$' -count=1 .
go vet ./...
staticcheck ./...
govulncheck ./...
```

Integration suite запускається лише з `DATABASE_URL` окремої тестової БД. Робочий екземпляр 8081 не оновлюється автоматично.

Джерела правил: [Google: перевірка crawler IP](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests), [OpenAI: призначення ботів та IP](https://developers.openai.com/api/docs/bots), [Product snippets](https://developers.google.com/search/docs/appearance/structured-data/product-snippet), [Article](https://developers.google.com/search/docs/appearance/structured-data/article), [Breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb).

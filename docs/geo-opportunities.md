# План SEO/GEO-робіт і спостережені зміни

## Завдання

Модель `local-opportunity-v1` поєднує `local-topic-v1`, збережені SEO-факти, локальне зіставлення, сутності й перевірені відмінності останнього нескасованого набору конкурентів. До 1000 запитів; результати джерела, зокрема 10 000+, перевіряються пакетами без старого ліміту сторінок. `checked_pages` містить кількість усіх перевірених SEO-результатів домену, включно з невдалими. Показується до 500 завдань. За перевищення ліміту відображення пріоритет надається високим, потім середнім завданням; обмеження явно показане, перевірка корпусу не припиняється. Це редакторський план, не автоматичне внесення змін на сайт.

- Високий пріоритет: невдала HTTP-перевірка або явні технічні обмеження Google AI / ChatGPT Search. Спочатку перевірте призначення сторінки; `noindex` чи robots-заборона може бути свідомою.
- Середній: перевірені контентні прогалини, відсутній кандидат у вибраному аудиті, близькі цілі, спостережена відмінність конкурента та контекстна перелінковка.
- Низький: допоміжна metadata/schema й узгодженість сутностей. Спеціальна GEO-schema не є вимогою.

Завдання для тієї самої цілі й сигналу об'єднуються: до 12 запитів, 6 кластерів і 8 доказів. ID завдання стабільний для його типу/цілі/сигналу в цьому наборі; Target ID не є глобальною ідентичністю між аудитами. Експорт містить версії моделей і neutralization формул CSV. Unknown не перетворюється на missing; присутність сигналу конкурента не доводить перевагу в рейтингу або цитуванні.

Впевненість `high / medium / low / unknown` описує конкретну підставу: прямий HTTP-факт, повноту лексичного збігу, близькі кандидати, наближені терміни та обмеження вибірки. Це **не калібрована ймовірність**, не прогноз ефекту та не підтвердження AI-видимості.

## Перелінковка

Потрібен завершений Site Crawl-граф. Для знайденої цілі з не більше ніж двома **спостереженими** вхідними посиланнями аналізуються тематичні сторінки того самого корпусу. До трьох джерел на ціль, до 200 пропозицій. Мінімум 50% термінів та IDF-зваженого покриття; source content має бути придатним для аналізу. Уже збережене ребро, навіть nofollow або redirect, виключає пропозицію. Поріг ≤2 є евристикою, не вимогою пошуковика.

Ребра зіставляються через Target ID та fingerprint, не замаскований URL. Неповний graph/HTML і наближений збіг знижують впевненість. Query-URL не пропонується як готове посилання: замаскований параметр не можна відновити. Анкор — вихідний запит, який редактор має адаптувати до речення; це не вигаданий знайдений фрагмент. Намір і відсутність посилання потрібно перевірити на реальному сайті.

## Ручний вибір цілі

У звіті відкрийте «Обрати ціль вручну», оберіть запит, успішну HTTP 200 HTML-сторінку того самого source run / домену та пояснення. Target ID показаний окремо, бо замасковані URL можуть збігатися. Ручний вибір переоцінює фактичний lexical coverage: нерелевантна сторінка не стає релевантною через саме призначення.

Append-only журнал містить початковий автоматичний результат окремо, CAS-ревізію та ідемпотентний UUID рішення. Повтор того самого запиту не дублює запис; застаріла ревізія повертає 409. До 100 рішень на запит. Пояснення проходить URL redaction. Скасування ручного вибору — нова подія, не видалення історії. Рішення дозволено лише для поточної версії моделі; для старої створіть новий звіт.

Ручний вибір змінює поточну таблицю, карту покриття, план, CSV та порівняння конкурентів. Не змінює збережені SEO-результати, первинний automatic GEO-result, автоматичні події профілю чи історичні імпорти/цитування. Ручні AI-спостереження стосуються запиту/бренду, не є доказом цитування нової вручну обраної сторінки.

## До / після

Потрібен попередній GEO-звіт того самого домену. Числове delta доступне лише за однакової моделі, способу вибору, повної вибірки, кількості сторінок корпусу й fingerprint/key ID цілі. Зміна лише секретного параметра розрізняється навіть за однакового safe URL. Після ротації ключа ідентичність невідома. Відсутня ціль або зміна алгоритму не отримує вигаданий нуль.

Навіть однакова кількість сторінок не означає незмінний IDF-корпус. Зміна оцінки або сигналів — спостереження, не доказ причинного ефекту виконаного завдання. Інтерфейс не заявляє причинного ROI чи зміну позицій.

## Графік AI-спостережень

Останні 50 періодів одного домену, джерела, системи, країни, пристрою та рівня даних. Для однакового періоду береться останній імпорт, який містить вибраний рівень: URL-only імпорт не замінює дані query. Якщо запиту немає в останньому імпорті його рівня, значення невідоме; старий показник не підставляється. Значення різних періодів не підсумовуються; перекриття позначені. Відсутній/неприв'язаний рядок та порожній показник — невідомі, explicit 0 залишається 0. `gsc_web` не допускається до AI-графіка.

- `query`: лише явно прив'язаний запит.
- `query_url`: сума явно імпортованих рядків цього запиту та URL, не вибір лише поточної target page.
- `url`: лише ідентичність поточної цільової сторінки, без атрибуції показів запиту. URL зіставляється через fingerprint/key ID, а не safe URL. Ротація ключа або відсутня прив'язка дає unknown.

GSC AI URL-only дані не містять підтвердженого query/clicks: ці поля не вигадуються. Readiness не входить до графіка. До 5000 рядків на імпорт. Автоматичного збору AI-видачі, платних API та прогнозу цитування немає.

## Регресійний benchmark

`internal/geo/testdata/lexical-benchmark.csv`: 120 **синтетичних** англомовних запитів, 12 контрольних тем і очікувані цілі. `TestLexicalBenchmark` перевіряє top-1 accuracy та pairwise precision/recall/F1 кластеризації; у логах є версії моделей. Цей простий набір знаходить регресії, але не є незалежною людською розміткою й не оцінює реальну точність рекомендацій на клієнтських сайтах. Для такої оцінки потрібен окремий вручну розмічений набір, зокрема українські, неоднозначні та unmatched запити; його ще не надано.

```powershell
go test -v ./internal/geo -run TestLexicalBenchmark -count=1
go test -race -count=1 ./...
go test -tags=integration -run 'TestGEOTargetDecisions|TestGEOOpportunity|TestGEOVisibilitySeries' -count=1 ./...
```

Integration виконуйте лише на окремій тестовій PostgreSQL.

## API та оновлення

Усі маршрути використовують наявний token/same-origin захист:

- `GET /api/geo/reports/{id}/opportunities`
- `GET /api/geo/reports/{id}/tasks.csv`
- `GET /api/geo/reports/{id}/targets?search={text}&after={target_id}`: пошук і keyset-пагінація успішних сторінок джерела; до 50 цілей та `next_after` за відповідь. `total` — повний корпус звіту, не кількість збігів пошуку.
- `POST /api/geo/reports/{id}/queries/{ordinal}/target`: `id`, `target_id` або null, `expected_revision`, `reason`.
- `GET /api/geo/reports/{id}/queries/{ordinal}/target-history`
- `GET /api/geo/reports/{id}/impact?baseline={report_id}`
- `GET /api/geo/reports/{id}/visibility-series?ordinal=1&source=ai_observed&engine=chatgpt&country=US&device=all&scope=query`

Міграція 22 створює журнал і зв'язки, не змінює попередні міграції чи результати. Міграція 24 додає [пакетний PostgreSQL-індекс](geo-corpus.md), 25 — підписи дублів, 26 — snapshot відбору конкурентних сторінок, 27 — індекс FK для каскадного видалення великих корпусів. Перед оновленням потрібен backup. Поточний binary очікує схему 27; відкат потребує відповідного binary та послідовних Down-міграцій або restore. Down 23→22 видаляє міжнародні evidence, а Down 22→21 — журнал ручних рішень і його constraint; SEO/GEO-результати й імпорти зберігаються. Retention source run каскадно видаляє пов'язаний журнал. Основний runtime не оновлюється автоматично, git push не виконується.

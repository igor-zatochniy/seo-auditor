# Теми, GEO-моніторинг і конкуренти

## Карта покриття

Модель `local-topic-v1` працює без AI API: нормалізовані українські / англійські словоформи, IDF за набором запитів, cosine similarity та complete-link. Кожна пара у кластері потребує ≥2 спільних термінів і similarity ≥0,45; однакові однослівні запити допускаються. Транзитивний «місток» не об'єднує несумісні теми. До 1000 запитів, до 24 термінів на запит. Представник — реальний запит, не згенерована семантична назва. Синоніми та переклад не моделюються.

- Покрито: ціль знайдена, lexical coverage та IDF-зважене покриття ≥80%, без ambiguity/limited.
- Частково: ціль знайдена, але попередні умови не виконані.
- Без цілі: відповідного кандидата не знайдено **у вибраному аудиті**. Це не доказ відсутності сторінки на сайті.
- Основний URL — найбільше зіставлених запитів. Близькі кандидати — альтернативи ambiguous-запитів зі збігом ≥50% та різницею релевантності ≤10. Це не встановлена SEO-канібалізація.

Карта обчислюється на читання зі збережених GEO-результатів і останніх явних ручних рішень, якщо вони є. Початковий автоматичний результат незмінний. SEO-лічильники й автоматичний timeline не перераховуються. [План робіт, журнал рішень і перевірка змін](geo-opportunities.md).

## GEO-профілі

Створіть SEO-розклад у `/monitoring`, потім GEO-профіль на `/geo` або в GEO-звіті. До 100 профілів, до 10 на розклад. Домен має відповідати цілям розкладу. Запити, бренд і домен незмінні; для іншого набору створіть новий профіль. Пауза впливає лише на майбутні SEO-запуски; вже записані jobs обробляються.

Зв'язок `profile → scheduled run` створюється у транзакції запуску SEO. Для нового профілю також аналізується останній завершений запуск розкладу. GEO-звіт, події та `ready` фіксуються однією транзакцією з наперед визначеним report ID. Втрата відповіді COMMIT не створює дублікат. Jobs обробляються у порядку запусків профілю; зайнятий GEO-lock не витрачає спробу. Помилки аналізу мають до 3 спроб, потім доступне ручне повторення. Невдалий SEO-запуск позначається `interrupted` і не стає baseline.

Автоматичні події: зміна замаскованого Target URL, релевантності, перевірених правил Google AI / ChatGPT Search / OAI-SearchBot, бренду в основному контенті, кількості блоків із ≥50% термінів запиту. Неповна вибірка не означає зникнення блока. Baseline лише з тією самою моделлю зіставлення; різні model IDs у timeline не є порівнюваними шкалами. URL після маскування не дозволяє виявити зміну лише секретного query-параметра.

Історія показує останні 50 запусків; timeline — до 10 завершених звітів, по 50 запитів на сторінку. Для GEO потрібен завершений SEO-аудит із ≤1000 успішних HTML-сторінок. Більше джерело явно відхиляється, не аналізується потай частково.

Окремі події сутностей відстежують перевірені стани Organization, sameAs, publisher, author і Product.brand. Згадка бренду у видимому контенті залишається окремим сигналом. `Unknown` не вважається зникненням сутності; поява розмітки не доводить достовірність чи експертність бренду.

### Спостережена AI-видимість

Ручні `yes ↔ no` порівнюються тільки для тієї самої AI-системи між звітами профілю; `unknown` або відсутня перевірка не є втратою. Показується останнє явне спостереження кожного звіту; нові спостереження можуть змінити цей live-висновок.

Для імпортів порівнюються останній AI-імпорт поточного звіту та останній сумісний імпорт baseline: однакові джерело, AI-система, країна й пристрій, неперекривні періоди. Лише explicit `0 ↔ >0` показів; відсутній рядок чи `null` не прирівнюється до нуля. `gsc_web` виключено. URL-only дані не приписуються запитам. URL зіставляється через збережені HMAC fingerprint та key ID, не через замаскований текст. Після ротації ключа URL-порівняння пропускається. Це спостереження у вибраних імпортах, не доказ постійної втрати/отримання видимості. Імпорт та ручні перевірки залишаються явними діями користувача, автоматичного зовнішнього моніторингу AI-видачі немає.

## Конкуренти

Додайте 2–5 окремих доменів або URL, по одному на рядок: `example.com | Бренд`. Власний домен / його піддомени, credentials, query-параметри, дубльовані домени й заборонені мережеві цілі відхиляються. Для міжхостового редиректу вкажіть кінцевий URL.

Домен: BFS до глибини 2, за замовчуванням 25 сторінок, максимум 50, без sitemap та JavaScript. Конкретний path URL: одна сторінка. Один активний crawl на AuditManager; заплановані SEO-аудити мають пріоритет. Черга — до 100 активних competitor jobs, до 20 наборів на вихідний GEO-звіт. Початковий SEO-аудит не змінюється.

Свіжість за замовчуванням 24 години, дозволено 1–168. Повторно використовуються лише завершені аудити з успішним точним target fingerprint поточного ключа та сигналами v3. Для домену додатково перевіряються root URL і не менші page/depth межі, без sitemap. Старі/невдалі/несумісні аудити не підходять. Freshness — дата закінчення аудиту, не гарантія незмінного контенту. У UI видно повторне використання і source run.

Створення source run, snapshot і claim job атомарне; наперед збережений run ID запобігає повторному crawl після невизначеного COMMIT. Після crash stale run проходить наявний recovery; job стає failed, повторення явне. Скасування прибирає pending jobs і зупиняє власний активний crawl цього процесу; reused shared audit не скасовується. У розподіленому запуску скасування вже працюючого crawl іншого процесу може чекати його завершення; GEO-аналіз скасованого набору не публікується.

Порівняння використовує той самий перелік запитів. Розбіжності показуються лише між перевіреними сигналами двох знайдених цілей: структура, entities, crawler eligibility, блоки відповіді. Unknown не стає missing. Зовнішнє посилання не оголошується «первинним доказом»; релевантність різних IDF-корпусів не визначає переможця. Немає scraping видачі, платних API або автоматичного підтвердження цитування.

## Оновлення та перевірка

Міграція 20 не змінює попередні SQL-файли й дані. Перед оновленням потрібен backup. Старий binary зі схемою 19 потребує контрольованого Down 20→19 або відновлення backup. Down видаляє GEO-профілі, jobs і зв'язки конкурентів, але зберігає згенеровані SEO/GEO-звіти та CSV-імпорти.

```powershell
go test -race -count=1 ./...
go vet ./...
staticcheck ./...
govulncheck ./...
go test -tags=integration -run 'TestGEOProfiles|TestGEOCompetitors|TestGEOStrategy' -count=1 ./...
```

Integration запускайте тільки на окремій тестовій PostgreSQL. Основний runtime не оновлюється автоматично й GitHub не публікується під час розробки.

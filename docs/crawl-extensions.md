# DOM-обхід, URL-маршрути та польові Core Web Vitals

## Вартість і активація

DOM-обхід та URL-діагностика виконуються локально без платних API. Chromium потребує CPU/RAM; це не безкоштовний хмарний сервіс. CrUX API надається Google без оплати за запити, з квотою 150 запитів/хв на проєкт. Потрібні Google Cloud project, увімкнений Chrome UX Report API та API-ключ. Не публікуйте ключ, обмежте його цим API і зберігайте лише локально в захищеному `.env`:

```ini
CRUX_API_KEY=
```

Порожній ключ вимикає зовнішні CrUX-запити, але не SEO, GEO чи rendering. Ключ не передається браузерному UI, не зберігається у звітах/БД і не додається в URL запиту до Google. Використовується `X-Goog-Api-Key`.

## Обхід DOM-посилань

Для Site Crawl є окремий перемикач **Обхід DOM-посилань**. Він потребує увімкненого JavaScript та наявного ізольованого Chromium. Таку саму опцію має звичайний розклад Site Crawl; адаптивні часткові списки залишаються HTML-only.

Зібраний frontier є об'єднанням HTML та DOM-посилань. Однакові спостереження не дублюють edges; повторні однакові посилання, які вже були у HTML, зберігають свою множинність. Граф показує джерело `html`, `rendered` або `both`. Початкові title, description, word count та інші SEO/GEO-метрики не замінюються DOM-значеннями.

Загальний ліміт — 256 посилань на сторінку; HTML має пріоритет. Перевищення або partial/failed rendering позначають неповну discovery, не приховують її. Нові цілі додаються у тій самій транзакції, що й результат сторінки, і під тим самим ownership fence. Зберігаються max pages/depth, same-origin, HMAC дедуплікація, nofollow, robots.txt, DNS/private-IP validation та per-host policy. Resume використовує збережений режим, не нове значення ENV.

Це обхід `<a href>` із знімка DOM у наявному обмеженому вікні. Кліки, форми, scroll, POST, cookies користувача, Shadow DOM, усі стани SPA та нескінченні таймери не моделюються. Знімок не є емуляцією Googlebot або доказом індексації.

Renderer зберігає до 16 причин невдалого ресурсу: тип, безпечний URL, стабільний code та HTTP-код. Немає body/headers/cookies. Перевищення цього списку й скорочення URL позначаються явно. Політики renderer не послаблені; зокрема заблокований нашою політикою ресурс не означає, що він недоступний Google.

## URL-маршрути

Нова вкладка показує redirect і canonical маршрути **лише за результатами цього run_id**. Невідомі цілі автоматично не завантажуються. API читає 25 початкових сторінок keyset-пакетами, до 512 сусідніх спостережень і 10 переходів; SQL lookup використовує binary fingerprints та індекс. Інші runs/ключі не підставляються як підтвердження.

Діагностика відрізняє self-canonical, відсутній canonical, цикли, HTTP 4xx/5xx цілі, noindex Google, некоректну адресу, неоднозначні результати, неперевірену ціль і ліміт вибірки. HTML та HTTP `Link` canonical порівнюються окремо. HTTP Link parser обмежений 8 КіБ і 8 canonical; параметр `anchor`, некоректні quotes та oversize позначають неповну перевірку. Це не повна підтримка всіх розширень RFC 8288.

HMAC від оригінальної нормалізованої адреси формується до redaction. Публічні URL маскуються, а query variants не зливаються. HTTP Link canonical повинен бути абсолютним без fragment. Різні відомі canonical джерела показують конфлікт; sitemap із non-self canonical — кандидат для ручної перевірки, не автоматична SEO-помилка. Перевірка не визначає canonical, який фактично обрав Google. Rendered canonical залишається у окремому HTML→DOM порівнянні.

Вхідні посилання й список сторінок-джерел стосуються тільки зібраного Site Crawl graph. Нуль для спискового аудиту або неповного графа не доводить orphan. Історичні результати без нових URL-signals можуть показувати неповну перевірку; потрібно повторно сканувати, а не вигадувати старі HTTP headers.

## Польові CWV

CrUX завантажується лише кнопкою після підтвердження **Надіслати публічну адресу до Google**. GET історії не звертається до Google. Query/fragment вилучаються; приватні та credential URLs заборонені. Не використовуйте для конфіденційних, авторизованих або одноразових сторінок: секрет також може міститися у path.

Вибір `url` означає URL без query; `origin` — весь origin. Доменні дані не підставляються автоматично замість сторінкових. PHONE/DESKTOP зберігаються окремо. Відображаються p75 LCP, INP, CLS, поточний returned identifier, період збору та час отримання. Дані CrUX агреговані за rolling window, можуть бути відсутні через недостатнє покриття і не є виміром конкретного SEO-run або країни.

404 від CrUX — `no_data`, відсутня метрика — `partial`; жодне з них не означає погані CWV. Network/API errors не змінюють SEO-result і не перезаписують попередню good history. Відповідь обмежена 64 КіБ; в БД зберігаються лише вибрані числові метрики та bounded metadata. Кеш доступний 24 години, явне refresh обмежено одним запитом за 3 секунди на процес. Історія зберігається по run/target/device/scope/day, UI показує останні 14 спостережень; вікна можуть перекриватися.

Реальний API-ключ потрібен тільки для live CrUX. Unit/integration перевірки використовують synthetic provider responses без зовнішніх запитів і оплати.

## Міграції та відкат

Нові файли 035–037; поточний binary потребує schema 37. Випущені міграції 001–034 незмінні. Перед оновленням робочої БД зробіть backup. Відкат виконується лише після зупинки активних запусків та з узгодженим старим binary: Down 37 видаляє нові CrUX observations, Down 36 — URL-signals, Down 35 — DOM discovery flag/provenance. Для збереження цих нових даних потрібен backup. Контрольований retention старого audit run видалить також залежні CrUX observations через FK; новий автоматичний cleanup не запускається.

Джерела: [CrUX API і безкоштовна квота](https://developer.chrome.com/docs/crux/api), [API-key header](https://docs.cloud.google.com/apis/docs/system-parameters), [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

# PostgreSQL-індекс GEO

Опційні багатомовні поняття використовують цей самий повний корпус та IDF. Початковий лексичний результат зберігається окремо. [Методика розширень](geo-extensions.md).

## Повний корпус без ліміту 1000 сторінок

`local-lexical-v4/postgres-v1` зберігає похідні лексичні профілі у PostgreSQL, не повний HTML або `request_url`. Завершене джерело читається в стабільній транзакції `REPEATABLE READ`, keyset-пакетами по 32 сторінки. Кількість прочитаних успішних HTTP 200 результатів звіряється з `COUNT(*)`; неповний індекс не публікується. Інший домен виключається явно, піддомени входять до корпусу.

IDF враховує всі сторінки корпусу. SQL оцінює всіх кандидатів зі збігами й лише після ранжування вибирає три найкращі. Лексичні та фразові внески агрегуються незалежними потоками: це запобігає повторному скануванню всіх профілів на кожен target за відсутності статистики нового індексу. Сторінка без лексичного збігу не стає кандидатом лише через фразу. Формули, фрази, словоформи, fuzzy-пошук і tie-break за Target ID узгоджені з локальною моделлю; семантичні синоніми та переклад цей індекс не додає.

Індекс прив'язаний до SEO-запуску, домену й версії моделі. Джерело має бути завершеним і незмінним. Побудова індексу та створення GEO-звіту атомарні: скасування чи rollback не залишають часткового звіту. Повторний аналіз повторно використовує готовий індекс. Видалення source run каскадно видаляє його похідний індекс, не створює незалежних копій приватних URL.

## Що залишається обмеженим

- Один запит: до 300 символів; один звіт: до 1000 запитів.
- Профіль сторінки: до 256 термінів і 128 фраз. Title, description та H1 для індексу читаються до 8192 символів; початкові SEO-дані не змінюються. Обмежені профілі рахуються в `limited_pages`, відповідні зіставлення містять `matching.limited`.
- Fuzzy-пошук має bounded кількість порівнянь і знайдених варіантів; його обмеження не приховується як відсутність релевантної сторінки.
- У Go утримуються обмежені кеші словника/частот і до 32 hydrated кандидатів, не всі сторінки або ребра графа.
- Важкі GEO-операції мають загальний deadline 5 хвилин. Перевищення не створює частковий успішний звіт; це не гарантія часу виконання для довільного корпусу.
- План робіт перевіряє всі SEO-результати домену пакетами по 128, включно з невдалими. Показується до 500 завдань і 200 рекомендацій перелінковки; це ліміт відображення, не обрізання перевіреного корпусу.
- Ручний вибір цілі використовує пошук і сторінки по 50 записів. Імпорт видимості зіставляє кожен URL через індекс БД, без великої RAM-мапи; неоднозначні fingerprints не прив'язуються до випадкової цілі.
- Порівняння «до/після» читає захищені ідентичності лише обраних цілей звіту, навіть якщо їхні Target ID розташовані наприкінці великого джерела. Відображення перших сторінок не обмежує це порівняння.

## Корпус не дорівнює всьому сайту

`report.corpus` показує `source_pages`, `pages`, `excluded_other_domains`, `limited_pages` та `complete`. `crawl_complete` і `crawl_warning` окремо описують повноту вихідного SEO-обходу. Для аудиту готового списку URL повнота сайту не підтверджена. Page/depth/sitemap/HTML-link limits не стають доказом відсутності іншої сторінки на сайті.

Старий звіт без manifest не позначається як повністю перевірений новим backend. Readiness і лексична релевантність не підтверджують фактичної AI-видимості; імпортовані та ручні спостереження залишаються окремими.

## Міграція й перевірки

`024_geo_corpus_index.sql` додає manifest, профілі, postings та dictionary із cascade FK до джерела, а також знімає старий constraint `page_count <= 1000`. Історичні звіти не переписуються. Down видаляє лише похідний індекс і не повертає constraint, який унеможливив би збереження нових великих звітів; старий binary потрібно оцінювати окремо перед відкатом.

Окрема міграція `027_geo_corpus_target_cascade_index.sql` індексує FK `(run_id, target_id)` до `audit_results`. Без цього індексу каскадне видалення великого source run багаторазово переглядає профілі. `028_geo_corpus_rank_index.sql` додає покривний індекс postings. Параметризоване читання термінів використовує його навіть до появи статистики нового corpus; ranking залишається повним, без попереднього усічення кандидатів. Попередні SQL-міграції не переписуються; поточний binary очікує схему 31, а індекс доданий у 024–028. Integration-тести перевіряють план ranking, наявність індексу FK і пакетне видалення власної фікстури на 10 001 сторінку. Кожна cleanup-операція має deadline 5 с; це не гарантія видалення всього великого запуску одним SQL за 5 с.

На окремій тестовій PostgreSQL:

```powershell
go test -tags=integration -run TestGEOCorpus -count=1 -timeout=10m .
go test '-tags=integration,qualitygate' -run TestQualityGateTenThousandURLsThousandQueriesFiveCompetitors -count=1 -timeout=25m .
```

`QUALITY_BROWSER=1` додатково запускає `TestGEOCorpusBrowserWorkflow` із Playwright: звичайний SEO-аудит, GEO на 10 001 сторінці, пошук останньої цілі, ручне рішення, desktop/mobile та екранування. Без браузера цей сценарій явно пропускається. На Windows можна задати `QUALITY_BROWSER_CHANNEL=msedge` і шлях підтримуваного Node.js через `QUALITY_NODE_EXECUTABLE`.

Перевірки охоплюють parity із resident-моделлю, 10 001 сторінку домену з найкращою ціллю наприкінці, ізоляцію доменів, ідемпотентність, rollback, пагінацію, ручний mapping, імпорт видимості та upgrade зі схеми 23 зі збереженням SEO/GEO-історії. Quality Gate потребує окремої БД та `SEO_QUALITY_GATE=isolated`; це не перевірка на реальних клієнтських сайтах.

# Типи сторінок, CDN та пакет виправлень

Усі модулі локальні, без платних API. PostgreSQL є основним сховищем. Початкові SEO-поля, лічильники й GEO-звіти не перезаписуються.

## Типи сторінок

Вкладка **Типи сторінок** у SEO-аудиті аналізує всі збережені результати вибраного origin пакетами по 128, без прихованого ліміту 1000. Показує 50 рядків на сторінку, загальні кількості типів та сигналів для перегляду.

Пріоритет: ручне уточнення target → перше відповідне правило → типи JSON-LD → слабка евристика сегмента URL. Типи: товар, категорія, стаття, послуга, інше, невизначено. Product/Article/ItemList можуть бути вкладеними сутностями, а не типом документа: кілька кандидатів залишаються невизначеними. Це не автоматично доведений CMS-шаблон. Ті самі типи можуть об'єднувати різні мовні розділи.

- Товар: Product JSON-LD, валідна ціна offers і розпізнане availability. OutOfStock є валідною заявою наявності, а не помилкою. Ринкова ціна й фактичний склад не перевіряються.
- Стаття: сигнал автора, валідна JSON-LD datePublished та зовнішні HTML-посилання як кандидати на джерела. Це не оцінка експертності/достовірності. Інші формати HTML-дати не оголошуються відсутніми.
- Категорія: внутрішні HTML-посилання та контекст існуючих графа й діагностики фасетних сімейств. Пагінація/фільтри не є обов'язковими для кожної категорії.
- Послуга: наявність зібраних блоків 300–500 символів; відповідність конкретним запитам перевіряється у GEO, не вгадується з типу URL.

Без повного HTTP 200 відсутність даних невідома. Старі JSON-LD snapshots не містять availability/date evidence і не перетворюються на хибні пропуски. Для нових полів потрібен повторний SEO-аудит. Автоматична модель: `page-types-v1`.

До 32 впорядкованих правил на origin/run: точний decoded path або префікс із кінцевим `*`, до 256 байтів, без query/fragment. Ручні уточнення мають обов'язкову причину. Оптимістична ревізія запобігає перезапису паралельної зміни. Зміни дозволені лише після завершення запуску; вони стосуються цього аудиту, не є глобальною настройкою профілю й не мають історичного журналу версій. Історичні від'ємні target_id також включаються до класифікації та підтримують ручне уточнення. Для їхнього повторного сканування пакет пропонує новий ручний аудит, а не непідтримуваний recrawl endpoint.

API:
- `GET /api/audits/{id}/page-types?origin=https://example.com&type=product&offset=0`
- `POST /api/audits/{id}/page-types/rules` — `{ "origin":"https://example.com", "revision":0, "rules":[{"pattern":"/products/*","type":"product"}] }`
- `POST /api/audits/{id}/results/{target}/page-type` — `{ "type":"article", "revision":0, "reason":"Перевірено власником" }`; `auto` повертає автоматичну класифікацію.

## Журнали CDN

Імпорт на `/bots`, вибір конкретного файлу у вкладці **Журнали CDN** SEO-аудиту. Немає автоматичного доступу до облікового запису CDN. Сам імпорт безкоштовний; доступність/повнота журналів залежить від провайдера й тарифу, sampling потрібно враховувати самостійно.

Формати та обов'язкові поля: [короткий контракт із прикладом](../web/static/cdn-formats.txt).

Підтримуються CloudFront standard TSV із `#Fields:`, Cloudflare HTTP requests Logpush JSONL, Vercel Drains HTTP `proxy` JSONL, Fastly **налаштований** JSONL за явним контрактом. Довільний Fastly/Vercel application-log не обіцяється. 8 МіБ, 10 000 записів, 32 КіБ на рядок. Імпорт із перевищенням відхиляється, не усікається. Обробляються GET/HEAD від розпізнаваних поточним модулем ботів; не всі можливі AI-клієнти. Invalid/nonbot/foreign/method/no-HTTP/duplicate лічильники показуються окремо.

Повторне завантаження того самого файлу ідемпотентне. Повторні request ID усередині файлу усуваються; суперечливий ID відхиляє весь імпорт. Різні файли з перекриттям не сумуються й не мають міжфайлового dedupe. Сирий файл, IP та request ID не зберігаються: лише безпечний URL, HMAC і обмежені факти. Cache status нормалізується за allowlist; інше — `other`, відсутнє — невідомо. CloudFront result type — результат edge, не доказ відповіді origin. HTTP 000 та OriginResponseStatus=0 не є HTTP 0/помилкою.

API `GET /api/audits/{id}/cdn-diagnostics?origin=https://example.com&import_id=UUID&offset=0` показує повторні 429/503, відмови 403/429/503, edge≥400 при origin 2xx та відмінності від збереженого HTTP 200 crawler. Вибір обмежений останніми 100 CDN-імпортами домену/його батьків до registrable domain, 50 груп на сторінку. Наприклад, імпорт `example.com` може містити події `www.example.com`, але у звіті вибраного origin відображаються лише його власні scheme/host/port, не сусідні піддомени.

Зіставлення лише за повним URL HMAC і key ID. URL із різними query values не зливаються. Якщо експорт не містить query, точне зіставлення буде неповним. Сам User-Agent не доводить справжність бота; перевірка IP використовує поточні опубліковані діапазони та явний невідомий стан. Різні час, IP, cookies і TLS-профіль crawler та журналу не дозволяють автоматично довести причину WAF/CDN.

Офіційні формати: [CloudFront](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html), [Cloudflare](https://developers.cloudflare.com/logs/logpush/logpush-job/datasets/zone/http_requests/), [Vercel](https://vercel.com/docs/drains/reference/logs), [Fastly](https://www.fastly.com/documentation/guides/integrations/streaming-logs/custom-log-formats/).

## Пакет для розробника або AI

У **Плані SEO/GEO-робіт**: Markdown, JSON, локальне копіювання Markdown. API: `GET /api/geo/reports/{id}/tasks.md` та `tasks.json`. Старий CSV працює як раніше.

Пакет містить run/report, версії моделей, дату генерації, обмеження плану, пріоритет/дію, конкретні URL та докази, дату збереженого target, HTTP/scan status, окремі response HTML / HTTP headers / rendered DOM, точні збережені meta/X-Robots директиви й доступні robots.txt policy evidence з датою/URL, критерії приймання та інструкцію ручної повторної перевірки. До 500 завдань — межа існуючого плану, явно `limited`. Поля є обмеженими витягами, не повним HTML; відсутній DOM або snapshot не вигадується. Новий аудит не запускається натисканням експорту.

Експорт не надсилає нічого зовнішньому AI й не редагує сайт. Недовірений контент позначається як дані, Markdown екранується, query values додатково маскуються. Це не захист від усіх можливих prompt injection і не автоматичний DLP: довільні персональні/конфіденційні тексти необхідно переглянути перед передаванням третій стороні. Історія task-пакетів у БД не зберігається; архівування завантажених пакетів залишається під контролем користувача.

## Upgrade та перевірка

Міграція `046_page_types_and_cdn_evidence.sql` додає окремі таблиці класифікації та nullable CDN-поля, розширює формат імпорту. Старі застосовані SQL-файли не змінюються. Поточний binary потребує схеми 46; backup перед оновленням обов'язковий. Down видаляє нові налаштування/edge-поля, зберігаючи базові старі SEO/GEO й bot imports/events. CDN-імпорти після rollback не можна повторно створювати старим binary; для повного повернення даних використовуйте backup.

```powershell
go test -race -count=1 ./...
go test -tags=integration -run 'TestPageTypeCDNAndRemediationFlow|TestSearchInsightsUpgrade' -count=1 .
node web/e2e/template-diagnostics.cjs
```

Браузерний тест вимагає власний preview (не 8081), `AUDITOR_BASE_URL`, `AUDITOR_ACCESS_TOKEN`, Edge/Playwright. Він створює лише власні тестові аудити й імпорти, не видаляє існуючі дані.
